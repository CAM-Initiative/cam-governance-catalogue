VIGIL Observatory · VIGIL-INC-000202

OSS-Fuzz-Gen evaluation exposed misleading crashes from invalid AI-generated test drivers

Between July and September 2025, researchers evaluated AI-generated fuzz drivers in OSS-Fuzz-Gen using Gemini 2.5 Pro and 1,555 benchmark functions from 336 projects. Some drivers violated internal functions’ calling requirements and produced crashes that were not reachable through normal application entry points.

The existing crash analyser also labelled some driver errors as program errors. The researchers added function constraints and contextual crash validation, reducing spurious results.

Their paper, published on 2 October 2025, reports roughly 70% false-positive crashes, although its prose and table assign the totals differently. No production outage or customer loss is reported.

Context

Figures 1–2 show the libraw example. The generated driver passes a buffer of arbitrary bytes into a function that casts the pointer to a CrxImage structure and accesses its fields.

A buffer that is too small can crash this test because the driver has not constructed the valid object expected by the function. Where normal callers enforce those conditions, the crash does not establish a defect reachable from the application’s entry point.

Sections 5.2.3 and 5.3.2 separately report that contextual validation rejected additional crashes initially classified as program errors.

Classified

The generated driver supplied arbitrary bytes where the target function expected a valid image object. A crash under that invalid calling condition establishes that the constructed test crashed, not that normal application use can trigger the same fault.

The evaluated workflow still labelled some such outcomes as program errors until a later validator examined their calling context. Treating the crash as application-defect evidence before establishing that connection gave the test artefact more diagnostic assurance than it supported.

The added validator traced one crash through the application entry point and found an input-length check that made the crashing path infeasible in normal use. It rejected that candidate with source-code evidence.

Conclusion

A crash in generated test code was treated as stronger evidence of an application defect than the calling conditions justified. The libraw example exposes the distinction: calling an internal function with arbitrary bytes can create an invalid state that normal application entry points would prevent.

Crash reproduction alone therefore did not establish that an application user could reach the defect. The later contextual validator examined that missing link and rejected additional crashes previously labelled as program errors.

This supports a diagnostic assurance problem in the evaluated workflow, without establishing a production outage or customer loss.

The added contextual check correctly rejected the documented infeasible path. Its sampled errors prevent treating all of its other decisions as verified.

The baseline diagnosis and the proposed remedy require separate assurance.

Governance significance

AI-generated tests can manufacture the conditions for a crash and then mislead later diagnosis if the workflow does not preserve those conditions. The testing system must distinguish a defect in its own test setup from a defect reachable through valid use of the application.

A useful check must examine how normal callers construct inputs and initialise state. Repeating the same invalid test confirms that the test crashes; it does not establish an application vulnerability.
