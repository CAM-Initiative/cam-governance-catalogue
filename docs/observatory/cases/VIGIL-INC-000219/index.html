VIGIL Observatory · VIGIL-INC-000219

Railway cloud platform intrusion and customer environment-variable exposure

From 18 to 22 October 2026, attackers probed and then breached Railway, a cloud platform for deploying applications. On 20 October, they escaped part of a build system's isolation, stole an internal credential and obtained portions of Railway's source code.

After Railway blocked that path, the attackers exploited a separate cloud-permission error to access further credentials, query customer environment variables and decrypt some of them. Railway says at most 1.85% of workspaces, around 100,000, could have had variables decrypted; this is an upper bound, not a confirmed victim count.

Compromised data also included linked-account tokens belonging to 1,852 users, and Railway estimated around US$740,000 in unauthorised spending with stolen API keys. Railway twice stopped new builds, revoked credentials and rebuilt affected systems; existing customer applications kept running.

Railway's later investigation described rapid parallel attack exploration involving safeguards-removed AI models and agent fan-outs, while leaving specific model actions and their human direction unverified.

Conclusion

The materialised mechanism was a multi-step external intrusion exploiting build isolation and overly broad internal credential trust, then accessing protected environment variables and linked account tokens. Railway's detailed account strengthens the evidence that the attacker used AI-assisted rapid exploration but still cannot attribute each exploit choice, privileged access or exfiltration action to an identifiable model or agent rather than the human operator.

That distinction keeps Fidelity Class findings unresolved while preserving the supported confidentiality, service disruption and financial consequences. Railway's own monitoring, emergency shutdown, revocation and rebuild are defender response, not successful Fidelity Class mappings to the attacking system.

Governance significance

The case illustrates how build credentials, stored workflow history, internal source code and cloud trust configuration can form a cumulative escalation route. Railway's expanded account also shows why materialised protected-data access and unauthorised AI-key spending can be assessed separately from the unresolved allocation of decisions between attacker and AI tooling.
